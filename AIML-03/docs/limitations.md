# Limitations and honest caveats

These are the things a reviewer should know before trusting any number in this repository.

1. **The A/B test is a simulation, not live traffic.** `final_eval.py` replays held-out interactions: a click means the shown item is one the user rated >= 4 in the evaluation window *and* the user examines that position (probability 1/log2(position+1)). It checks the assignment, logging and statistics machinery. It says nothing about real click-through. There are no real users here.
2. **Triton is verified, with limits.** Both rankers load on a real Triton 24.08 server and the full API ran on it with Redis, returning the same top-10 as in-process ranking (`results/live_triton_check.json`). It was run on CPU on a single laptop, with no load test and no in-process latency baseline on the same machine, so the 13.4 ms median is indicative only.
3. **The ranker gain shrank on the test window.** On validation the DCN-v2 ranker improved NDCG@10 over the best single retriever by +0.049; on the later test window it is +0.018 (still significant, interval 0.015 to 0.021). The rankers train on validation-window labels of other users, so part of the validation gain was window-specific.
4. **A classical baseline beats the two-tower on its own.** Item-based CF scores higher than the tuned two-tower (test NDCG@10 0.109 vs 0.086). The two-tower is kept because the brief asks for it and because it contributes complementary candidates (union candidate coverage 39.7% vs 36.5% / 38.6% alone on validation), not because it wins alone.
5. **Models are frozen at the train cut-off (2016-06).** The test window starts 2018-01, so test scores are for a model about 18 months stale (user histories are advanced; the item catalog, item statistics and weights are not). Items that first appear after the cut-off cannot be recommended and count as misses. Weekly retraining (the Airflow DAG) addresses this in production; it was not used to refresh the test numbers, to keep the test protocol simple.
6. **Cold-start quality.** Users with no likes get popularity (or genre-filtered popularity). It is measured (NDCG@10 0.387 on 12,709 validation newcomers, who mostly rate popular films first, so the number is not comparable with warm-user numbers) but it is not personalised. For users with 1 to 4 likes only 55 validation users have relevant items, too few to say whether the personalised route beats popularity (difference -0.025, interval -0.085 to +0.033).
7. **Candidate ceiling.** Rankers re-order 250 candidates that contain about 40% of each user's relevant items on validation, so Recall@100 can only rise so far.
8. **Evaluation protocol details.** Relevant = unseen items rated >= 4.0 in the window; recall's denominator includes relevant items outside the catalog. Metrics are macro-averaged over users who have at least one relevant item and at least 5 prior likes. Model selection used a 3,000-user validation sample; the first two-tower run (`tt_v1`, lr 2e-3) overfit after one epoch and was replaced by `tt_v2`.
9. **FAISS at this scale.** With 34k items exact search takes ~0.7 ms, so HNSW is not needed for speed here: its median is lower (0.41 ms vs 0.72 ms) but its slowest 1% is higher (4.4 ms vs 2.2 ms). It is in the pipeline because the brief asks for it and it matters at larger catalogs. HNSW can return fewer neighbours than requested for some queries (2 of 5,083 users at K=250), so the search retries and falls back to exact search.
10. **Data.** MovieLens 25M (ratings 1995-2019) is a single-domain, explicit-rating dataset; "likes" are ratings >= 4.0. No real click or impression logs exist, so "click-through" is only available through the simulation in (1).
11. **Data preparation at full scale.** `scripts/prepare_data.py` was run on the full 25,000,095-row `ratings.csv` and its output matches the arrays used for every result here (row count and a SHA-256 digest of each array; see `results/data_prep_verification.json`).
12. **Diversity re-ranking is a small effect.** `diversity` applies maximal marginal relevance over the ranker's top 50 using two-tower item vectors. On the 508 validation users the rankers never trained on, NDCG@10 stayed within noise down to lambda 0.6 (0.1842 to 0.1850) and fell at 0.5 (0.1806); genre diversity of the top 10 rose by only +0.0045 at 0.7 (interval +0.002 to +0.007) and +0.0109 at 0.5, while the share of films outside the 100 most popular fell from 0.656 to 0.629 at 0.7. So it mixes lists up a little and makes them somewhat more mainstream. It is off by default and was not run on the test window (`scripts/diversity_study.py`, `results/diversity_val.json`).
